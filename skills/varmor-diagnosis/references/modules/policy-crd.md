# VP / VCP / AP / APM and policy status

## 1. Object responsibilities

- **VarmorPolicy (VP)**: Namespace-scoped user policy protecting matching Deployments, StatefulSets, DaemonSets, or Pods in the same namespace.
- **VarmorClusterPolicy (VCP)**: Cluster-scoped user policy selecting targets across namespaces; it takes precedence over matching VPs.
- **ArmorProfile (AP)**: Internal enforcement object generated by the manager, containing actual Profiles, targets, and BehaviorModeling state, processed by agents.
- **ArmorProfileModel (APM)**: BehaviorModeling output with cross-node behavior models and generated Profiles. Large data may use local storage; interpret visibility through `storageType`.

Chain: `VP/VCP -> status.profileName -> AP with the same name -> agent node conditions -> Pod injection/runtime behavior`.

## 1.1 Lifecycle and priority

VP/VCP are declarative objects; AP is an enforcement object generated from current policy state. They are different resource layers. Changes usually traverse validation/matching -> AP create/update -> node loading -> new Pod injection or workload rollout. Lag anywhere may leave old and new settings coexisting.

- Correlate policy generation, condition timestamps, generated AP content, and manager reconcile evidence. Current VP/VCP status has no `observedGeneration`; old status or AP creation time cannot prove new settings were applied.
- Cross-namespace VCP targets may overlap namespace VPs. The current injector gives VCPs precedence and selects one policy rather than merging rules; verify final AP/profileName and Pod configuration for the deployed version.
- Policy deletion, mode changes, or target changes may leave AP, PodTemplate, and old Pod cleanup/updates temporarily unsynchronized. Residual APs or injection do not prove the current policy is still actively applied.
- APM is a modeling artifact, not an AP replacement in ordinary modes. After modeling, verify subsequent mode transition and Profile generation.

## 1.2 Evidence layers

Policy diagnosis cannot rely solely on overview names, modes, enforcers, and Ready summaries. Select detailed objects for the question:

- For policy design, built-in/custom rules, target, or enforcer configuration, read the VP/VCP details: the source of user-declared intent.
- To determine compilation or target loading, correlate VP/VCP `status` with AP details. AP is the manager-compiled implementation; do not treat its generated content as original user rules.
- For modeling results, read APM and interpret visibility using its status and storage type.

Same-named policies may differ by resource kind or namespace. Use the overview's actual `kind`, `name`, and `namespace`; do not guess AP names from naming conventions.

## 2. target semantics

- `kind` supports only Deployment, StatefulSet, DaemonSet, and Pod;
- `name` and `selector` are mutually exclusive and one is required;
- `selector` matches workloads using Kubernetes label-selector semantics;
- Empty `containers` usually includes all application containers; consider initContainers/ephemeralContainers separately;
- VP is namespace-limited; VCP can span namespaces;
- `spec.target` is immutable after creation; target changes are policy-lifecycle changes;
- Targets must also meet webhook matching labels/object scope. Use actual WebhookConfiguration, deployment settings, and version; example annotations alone are not evidence;
- Explicit target/container `unconfined` settings may override the policy; inspect both PodTemplate and actual Pod.

## 3. policy semantics

### Enforcer

Policies can combine `AppArmor`, `BPF`, `Seccomp`, and `NetworkProxy`. Combination names and availability vary by version/configuration. Do not infer capability from strings alone; check cluster settings and node capabilities.

### Mode

- **AlwaysAllow**: Adds no vArmor mandatory access controls and is useful as a comparison baseline; it does not disable other Kubernetes security mechanisms.
- **RuntimeDefault**: Uses vArmor's runtime baseline.
- **EnhanceProtect**: Primarily Allow-by-Default, strengthened with built-in and custom rules.
- **BehaviorModeling**: A separate stage collecting behavior over a specified duration and generating APM.
- **DefenseInDepth**: Deny-by-Default/allowlist protection from a behavior model or custom Profile; support depends on version and enforcer.

See `modules/policy-mode-profiles.md` for mode defaults, baselines, and enforcer differences. Use mode names in the deployed CRD. Current local source and official main docs include AlwaysAllow, RuntimeDefault, EnhanceProtect, BehaviorModeling, and DefenseInDepth. Do not substitute other products' or older versions' terminology.

## 4. Status semantics

VP/VCP:

- `status.profileName`: Generated Profile/AP name. Namespace policies often use `varmor-{namespace}-{policy}`, cluster policies `varmor-cluster-{namespace}-{policy}`; actual status is authoritative;
- `status.conditions`: Created, Updated, Ready, and other results. Read `reason/message` first when `status=false`;
- `status.ready`: Whether required agents processed the Profile; does not prove target Pods were injected;
- `status.phase`: Common phases include Pending, Modeling, Completed, Protecting, and Error/Failed;
- Before BehaviorModeling completes, do not assume ordinary mode transitions are available updates.

AP:

- AP shares the policy's `status.profileName`. In the official implementation, VP APs reside in the policy namespace and VCP APs in
  the vArmor component namespace. Use actual objects; section 2.1 of `playbooks/policy.md` gives minimal discovery when unknown.
- `status.desiredNumberLoaded`: Number of agents expected to process and respond;
- `status.currentNumberLoaded`: Number of agents reporting successful Profile processing;
- `status.conditions`: May contain failed-node `nodeName` and reason.

AP has no `status.ready` field. Assess nonzero desired/current counts, failure conditions, and the owning VP/VCP status together.

APM:

- APM uses the Profile name used for behavior reporting. Current VP/VCP APIs have no separate `status.armorProfileModel` field;
- `status.desiredNumber` / `status.completedNumber`: Expected and completed node-report counts;
- `status.ready`: Whether the behavior model and generated Profiles are ready;
- `status.conditions`: Node-level modeling state, possibly including `nodeName`, `reason`, and `message`;
- `storageType`: Top-level storage type, commonly `CRDInternal`, `LocalDisk`, or `PV/PVC`;
- `data.dynamicResult` / `data.profile`: Behavior results/generated Profiles under top-level `data`. External storage may leave complete content absent from the CRD.

## 5. Interpreting common failures

### Policy rejected or Ready=False

Check target kind/name/selector, mode-required fields, BehaviorModeling enablement/modelingOptions, DefenseInDepth configuration, enforcer combinations, NetworkProxy parameters, policy-name length, and webhook validation messages.

### Policy Ready=True but no protected targets

Distinguish empty selector results, missing matching labels, objects/namespaces outside webhook scope, unrecreated PodTemplates, explicitly unconfined containers, and VP/VCP overlap resolved according to the actual controller version.

### AP absent or persistently Pending

Usually points to no manager reconciliation/Leader, a policy not actually accepted, an unestablished target chain, or AP creation/update failure. Do not attribute directly to the agent.

### AP partially loaded

For `currentNumberLoaded < desiredNumberLoaded` or failed-node conditions, correlate each failed node with agent, kernel/LSM, runtime, Profile type, and node resources.

### Old protection remains after deletion/update

Inspect workload PodTemplates, bare Pods, old Pod ownerReferences, and SecurityContext. `updateExistingWorkloads` applies only to workload types supporting rolling updates; bare Pods need recreation.

## 6. BehaviorModeling investigation

Check containerd, BTF, audit sources, modeling flags, agent/classifier resources, and node coverage. For missing data, verify collection capability -> reporting -> manager aggregation/persistence separately. Modeling describes observed behavior; it proves neither completeness nor that observed actions should be allowed.
